## Requirements, analysis and design

| Concept | How it is used here | Where to look |
|---|---|---|
| Use cases with basic and alternative flows (L6-9) | Every feature is built from its use-case specification. A service method covers named steps, and each alternative flow has its own check and message. | `Diagrams and Use-Case Specifications.pdf`; `OfferService` (UC5 A1-A4 named in the code) |
| Domain class diagram (L3, L15) | The model classes follow the diagram: generalizations, constraints such as "at most 6 photos", derived attributes calculated on demand. | `models/`; `DataStore.getTotalViews` |
| State machine diagrams (L16) | Listing and Offer change status only through events that refuse invalid transitions. | `docs/state-machines.md`; `Listing.acceptDeal()` |
| Boundary, control and entity classes (L15) | Screens are boundaries, one control class per use case holds the rules, entities hold the data. Screens contain no rule. | UC5: `controllers/buyer/MakeOfferFlow` + `OfferDialogs` (boundary), `services/OfferService` (control), `models/Offer` (entity). UC7: `MyDealsView` asks for confirmation, `MyDealsService` decides, and tells the screen which buttons a deal gets (`Deal.canBeMarkedComplete()`). UC10: `ReviewSellerFlow` + `ReviewDialog` (boundary), `ReviewService` (control), `Review` (entity). Chat deal actions: `ChatView` + `OfferChoiceDialog` (boundary), `OfferAction` and `Conversation.offersToActOn` decide which offers and actions there are (control), `Offer` (entity). UC11: `DealHistoryView` (boundary), `DealHistoryService` with `HistoryQuery` and `HistoryEntry` (control), `Offer` and `Listing` (entities). UC9: `ReportListingFlow` + `ReportDialog` (boundary), `ReportService` (control), `Report` (entity) |
| Layers and subsystems; low coupling, high cohesion (L15) | `controllers` / `ui` → `services` → `data` + `models`; a lower layer never uses a higher one. Shared parts (card, chat, notifications, profile) exist once and are used by all three portals. | `README.md`, "Shared Core" |
| Active classes (L15) | The Timer actor of UC12 is an active class with its own thread of control, so deadlines are met whatever screen is open. Its changes are made in one store transaction, so the screens' thread and the timer never see half of each other's work. | `services/BorrowingDeadlineTimer` (active class) calls `BorrowingDeadlineService` (control) |
| Bridge classes for the implementation environment (L15) | `DataStore` talks to a `Storage` interface, so files, format and encryption can change without touching the rest. | `data/Storage`, `EncryptedJsonStorage` |
| Design principles (L17) | Program to an interface, not an implementation (`DataStore` knows only `Storage`; the borrowing-deadline timer writes its problems to a `Consumer<String>`, the console in the app); strive for loosely coupled designs (screens know services, never each other). | `data/Storage`; `services/BorrowingDeadlineTimer`; `controllers/buyer/BuyerDashboardController` |
| Open-closed principle (L18) | The shared chat calls each portal through interfaces it owns, so what a deal button does is the portal's business: the buyer's Agree to Counter starts Make Offer, and the seller's Respond in Offers & Requests opens the seller dashboard's offers screen, which the chat never sees. New portal behaviour plugs in without changing the chat. | `ui/ChatView.AgreeToCounter`, `ChatView.RespondToOffers` |
| Singleton (L18) | The app has one store, created lazily on first use. Adapted for testing: the constructors stay public, so each test makes its own store. | `DataStore.getInstance` |
| Observer (L17) | The simplest form: the borrowing-deadline timer is the subject and the dashboard on show its one observer, which reloads its screen. | `ui/LiveUpdates`, `ui/Refreshable`; `controllers/buyer/DealHistoryView` (refreshed when the timer returns an item, UC11 Special Requirement 1) |
| Mediator (L18) | Screens report what the buyer asked for through small interfaces, and the dashboard decides what opens next, so no screen knows another. | `BuyerDashboardController`, `MyDealsView.Actions` |
| Avoiding the God Class anti pattern (L18) | `DataStore` is the largest class, because it holds all the data. To keep it from growing, a use case's own queries go in its control class, which reads the store through `store.read`; each new screen is a class of its own. | `services/MyDealsService`; `services/DealHistoryService` (UC11's query reads the store through `store.read` instead of adding a `DataStore` method); `controllers/buyer/` |

## Implementation

| Concept | How it is used here | Where to look |
|---|---|---|
| Defensive programming: the barricade (L10) | Everything typed or clicked is untrusted. Services check it and answer with a `ServiceException` written for the user; behind them, model classes take clean values. | `OfferService.submitPriceOffer`, `Amounts.parse`, `ReviewService.submit` (deal, then rating, then comment); `ReportService.submit` (listing, then reason and details), with `DataStore.addReport` as the inner layer, which refuses a report on no listing or by an account that is not a buyer (regression log R10) |
| Assertions, preconditions and postconditions (L10) | Conditions that must never be false are checked as assertions or model-level exceptions, never used as input validation. | `OfferService.record`, `ReviewService.submit`, `ReportService.submit` (postconditions, and an impossible state: a report not added although it was checked under the same lock); `Listing` state checks |
| Design by contract (L10) | The interfaces between the shared chat and the portals state their preconditions and postconditions in their Javadoc, and the chat keeps its side: `chooseCounterAndAgree` asserts that the chosen offer is countered before calling `AgreeToCounter`, and `RespondToOffers` is only called with the chat's open offers. | `ui/ChatView.AgreeToCounter`, `ChatView.RespondToOffers`, `ChatView.chooseCounterAndAgree`; `docs/shared-core-for-seller.md` |
| Refactoring (L10) | Duplicates are removed when the second use appears. Long methods are split into named parts, and magic constants get names, with the behaviour checked to be unchanged. | `services/Amounts` (extracted from the Browse price filter when Make Offer needed it); `ui/ListingCard`; `AccountValidator.validatePassword` (split into named checks) and `AccountSnapshot.describe` (one method per section); colours named in `styles.css` instead of inline styles; `Dialogs.form` and `Dialogs.hint` (extracted from `OfferDialogs` when the review form needed them); `Fixtures.moveDealTo` (from `MyDealsServiceTest`, for `ReviewServiceTest`); `OfferText.terms` and `counterTerms` (extracted from `summary`, `counter` and `submitted` when the chat's offer dialog needed the terms alone); `ui/Choices` (the "All …" filter boxes, moved out of `BrowseView` when Deal History needed them); `models/RatingSummary` (a seller's rating count and average, which travelled as two loose values through five classes and could disagree, as one value that cannot hold an impossible pair) and Browse's `PriceRange` (the same for a price range's two optional ends); `testsupport/SameMoment` (the start-together thread pool that six critical-case tests each wrote by hand, five of them leaving threads running when the test failed); `services/ListingAccess` (which listings a buyer can open, moved out of `BrowseService` when Report Listing needed the same rule, with `BrowseServiceTest` unchanged as the check) |
| Code review (L10) | The shared core was reviewed against the specification; the review found R7. | `docs/regression-log.md`, R7 |

## Testing

| Concept | How it is used here | Where to look |
|---|---|---|
| Unit testing with drivers and stubs (L14) | JUnit classes are the drivers. `TestClock` replaces the real clock, so a 5-second borrow or a reminder 24 hours before a due date is tested without waiting (`BorrowingDeadlineServiceTest`); a store without storage replaces the files; a list replaces the console, so the timer's tests check exactly what it logs, and a passing run prints nothing. | `src/test/.../testsupport`, `PersistenceTest.CountingStorage`, `BorrowingDeadlineTimerTest` (its `problems` list) |
| White box: basis path testing and cyclomatic complexity (L12) | Decision-heavy methods get one test per independent path. JaCoCo measures branch coverage, and the build fails below 65%, both on the code that holds the logic and on the whole project. | `OfferService.checkPeriod` (complexity 5, five tests in `OfferServiceTest`); `DealHistoryService.inRange` (complexity 5, one test per path in `DealHistoryServiceTest`); `HistoryText.dealType` (four paths, `HistoryTextTest`); `ReportService` {Check Report} and {Check Details} (six decisions, V(G) = 7, one test per path in `ReportServiceTest`); `target/reports/jacoco` |
| Black box: equivalence partitioning (L13) | Inputs are split into valid and invalid partitions from the specification, and each is tested at least once. | `OfferServiceTest` (price: nothing typed / not a number / not positive / positive), `AmountsTest`, `AccountValidatorTest`, `ReviewServiceTest` (rating: none / below / in / above the range; comment: none / blank / text; whose deal; who is logged in), `DealHistoryServiceTest` (who is logged in; date range; category; seller text: none / blank / the whole name / part of it in another case / no match; the seller's account active / deactivated / deleted), `ReportServiceTest` (who is logged in; the listing; who reported it before; reason: none / each of the six; details: none / empty / blank / text) |
| Black box: boundary values (L13) | Values at, just below and just above each boundary. | `OfferServiceTest`: price -0.01 / 0 / 0.01; period 4 s / 5 s / 6 s; start now - 1 s / now / now + 1 s. `MyDealsServiceTest`: self-return 1 s before the due date / at it / 1 s after. `ReviewServiceTest`: rating 0 / 1 and 5 / 6, and a comment of one character. `DealHistoryServiceTest`: each end of the date range on the deal's day / the day before / the day after, a one-day range, a start one day after the end (A2), and 23:59:59 / 00:00:00 at the end of a day. `HistoryTextTest`: 0 / 1 / 2 deals. `ReportServiceTest`: details empty / only spaces / one character |
| Black box: thread testing (L13) | A test follows one use-case flow through all the objects it touches, often across roles. | `MyDealsServiceTest.oneDeal_fromOfferThroughAcceptanceToCompletion_acrossThreeUseCases`, `OfferServiceTest.offerThenAcceptance_acrossBothRoles_endsWithAReservedListing`, `ChatServiceTest`, `NotificationBoardFlowTest`, `ReviewServiceTest.oneDeal_fromTheBuyersOfferToItsReview_acrossFourUseCases` and `anItemTheTimerReturned_isOfferedForReview_untilItIsReviewed`, `DealHistoryServiceTest.aPurchase_fromTheBuyersOfferToTheHistory_acrossThreeUseCases` and `anItemTheTimerReturnedLate_isDatedOnItsDueDate_notWhenTheTimerRan`, `ReportServiceTest.aReport_fromTheDetailScreen_toTheAdminsBoard_andTheAdminsViewOfTheListing` (from the buyer to the admin) |
| Black box: state-based testing (L13) | The object is first put into each state through its state machine, then the event is applied and the resulting state checked. | `ListingStateMachineTest`, `OfferServiceTest.listingThatIsNotLive_acceptsNoOffer`, `MyDealsServiceTest` (a deal in each of its five states, with "mark complete" and "return" applied to each); `ReviewServiceTest` (a deal in each state, then "review": allowed only when completed and not reviewed yet); `OfferActionTest` (each kind of offer in each state, with the actions offered to the seller and to the buyer); `DealHistoryServiceTest` (each kind of deal in each state: only a completed one is in the history, whatever its listing's state becomes later) and `HistoryEntryTest`; `ReportServiceTest` (a listing in each state, with and without the buyer's deal: it can be reported exactly when UC8 opens it) |
| Integration testing: sandwich, critical subsystems (L14) | The shared middle is tested bottom-up with drivers while the portals are built on top. The critical parts (deal lifecycle, concurrency, saving) have their own tests. | `README.md`, "How We Build and Test"; `OfferServiceTest.claimsSubmittedAtTheSameMoment_onlyTheFirstSucceeds`, `ReviewServiceTest.reviewsOfOneDealSubmittedAtTheSameMoment_onlyTheFirstIsRecorded`, `ReportServiceTest.reportsOfOneListingSubmittedAtTheSameMoment_onlyTheFirstIsRecorded`; a contract test between the buyer-built chat and the seller's service: `OfferActionTest.everyAnswerTheChatOffers_isOneTheSellersServiceAllows_andNoOther`; `DealHistoryServiceTest.theHistoryReadWhileTheTimerReturnsItems_seesAllOfThemReturnedOrNone` (the timer and the screens in one store). All of them run their threads through `testsupport/SameMoment`, which stops them even when a test fails |
| Regression testing (L13-14) | Every bug is reproduced, recorded with its input and correct output, and kept as a test. All tests run on every build. | `docs/regression-log.md` (R1-R11; R8 to R11 were reproduced as failing tests before the fix, R9 from a recorded acceptance-test run) |
| System and acceptance testing (L14) | System tests run the real screens in a window nobody sees, on the demo data in a temporary folder: a demo user of each portal logs in on the welcome screen and opens every page, and each buyer use case runs through its screens with its alternative flows, forms filled in and submitted. Acceptance tests are manual scenarios through the screens, one per flow of each use case. | `PortalScreensTest`, `controllers/buyer/*ScreensTest` (`testsupport/OffScreenApp`, `ScreenData`); `docs/acceptance-tests.md` |
